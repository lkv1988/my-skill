# 问题修复

[English](problem-fixing.md)

## 先判断问题与修复归属

遇到异常或阻碍时，先结合实际目标判断：这是否是需要解决的问题，是否影响目标，由谁负责，其修复是否属于当前工作范围。不要把每一个遇到的现象都自动转化为修复任务，也不要默认应通过修改当前工程来消除每一个障碍。

根据证据确定恰当的处理方式与修复位置。查明根因不等于接管根因所在组件的修复责任。范围内且判断明确的工作直接执行；需要改变目标、范围或重要取舍时，再与协作者讨论。

- **正例：** 被调用 CLI 内部崩溃，调用方明确报告调用失败并保留必要诊断信息，将缺陷指向 CLI；需要修复 CLI 时，按相应工作范围处理。
- **反例：** 调用方匹配 CLI 的崩溃堆栈，为其增加特殊分支、补偿流程，并把内部错误自行解释成用户输入问题。

## 查明并解决根因

不能停留在表面观察，应查明真正根因后再选择修复方案。从底层问题出发考虑正确的解决方式，避免仅修补可见症状、治标不治本。

禁止用不当 Mock 绕过失败，或让测试通过却留下底层问题。

始终以工程项目持续正确地演进为目标，不能只让眼前任务看起来已经完成。表面修复或测试通过，都不能证明问题已经真正解决。
